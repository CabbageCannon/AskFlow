# AskFlow Adaptive Research - Future Extensions

> 本文件记录当前 **Adaptive Research Termination + Targeted Re-Research** 功能中暂不实现、后续可继续优化的工程点。
>
> 当前原则：先完成稳定可运行的第一版主流程，再逐步优化 LangGraph 原生编排与 Researcher 输出协议。

## 1. Targeted Research 改为 LangGraph `Send` 动态 Fan-out

### 当前实现

第一版计划在 `targeted_research()` 节点内部：

```python
research_jobs = [
    researcher_subgraph.ainvoke(...)
    for task in tasks
]

results = await asyncio.gather(
    *research_jobs,
    return_exceptions=True,
)
```

即：

```text
plan_targeted_research
        ↓
targeted_research
        │
        ├─ researcher_subgraph(task A)
        ├─ researcher_subgraph(task B)
        └─ researcher_subgraph(task C)
        ↓
evidence_verifier
```

### 当前实现的问题

- 多个 Researcher 的并行执行被封装在一个 LangGraph node 内部。
- Studio 图上只能看到一个 `targeted_research` 节点，无法直接观察每个 targeted worker。
- worker 粒度的 tracing / checkpoint / state aggregation 不够清晰。
- 与 LangGraph 原生 orchestrator-worker / map-reduce 模式相比，可观测性较弱。

### 后续优化方向

考虑使用 LangGraph `Send` 动态 fan-out：

```text
plan_targeted_research
        ↓
   dynamic Send
   /     |      \
  ↓      ↓       ↓
worker  worker   worker
  \      |       /
        merge
          ↓
evidence_verifier
```

每个 `TargetedResearchTask` 动态生成一个 worker。

重点研究：

- `Send` 的动态节点派发方式；
- worker state 与 `AgentState` 的映射；
- `notes` / `raw_notes` reducer 如何汇总；
- 多 worker 完成后的自动 barrier / fan-in；
- Studio 中每个 targeted task 的可视化与 tracing；
- 是否直接把 `researcher_subgraph` 作为 worker，还是增加一层 adapter node。

## 2. Researcher 输出协议结构化，取消字符串错误判断

### 当前实现

`compress_research()` 压缩失败时会返回类似：

```python
{
    "compressed_research":
        "Error synthesizing research report: Maximum retries exceeded",
    "raw_notes": [raw_notes_content],
}
```

调用方目前可能通过：

```python
compressed_research.startswith(
    "Error synthesizing research report"
)
```

判断压缩是否失败。

### 当前实现的问题

这是 stringly-typed error handling：

- 错误文案修改会破坏判断；
- `compressed_research` 同时承载“业务结果”和“错误状态”，语义不纯；
- 无法清晰区分：
  - Researcher 整体执行异常；
  - Researcher 已拿到 raw evidence，但 compression 失败；
  - Researcher 正常完成；
- compression 失败并不等于研究完全失败，`raw_notes` 仍可能具有价值。

### 后续优化方向

优先考虑给 `ResearcherOutputState` 增加明确状态字段，例如：

```python
class ResearcherOutputState(BaseModel):
    compressed_research: str = ""
    raw_notes: list[str] = []
    compression_succeeded: bool = True
    compression_error: str | None = None
```

正常压缩：

```python
{
    "compressed_research": "...",
    "raw_notes": [...],
    "compression_succeeded": True,
    "compression_error": None,
}
```

压缩失败但存在 raw evidence：

```python
{
    "compressed_research": "",
    "raw_notes": [...],
    "compression_succeeded": False,
    "compression_error": "Maximum retries exceeded",
}
```

进一步可评估是否升级成：

```python
status: Literal["success", "partial", "failed"]
```

但第一阶段不急于增加过多状态。

### 最终目标

让调用方通过结构化字段判断：

```text
subgraph 未捕获异常
    → 整个任务执行失败

subgraph 正常返回 + compression_succeeded=True
    → compressed + raw evidence 可用

subgraph 正常返回 + compression_succeeded=False
    → compression 不可用，但 raw evidence 仍可保留
```

避免任何基于错误字符串前缀的流程控制。

## 3: Evidence Verifier Structured Output Robustness

### Background

The current `evidence_verifier` node uses LangChain structured output:

```python
verification_model = (
    configurable_model
    .with_structured_output(VerificationResult)
    .with_retry(...)
)
```

and expects:

```python
verification_result = await verification_model.ainvoke(...)
```

to return a valid `VerificationResult`.

During real LangGraph Studio testing, an edge case was observed where:

```text
evidence_verifier
↓
LLM HTTP request succeeds (200 OK)
↓
structured output does not produce a valid VerificationResult
↓
verification_result = None
↓
route_after_verification
↓
missing_verification_result
↓
final_report_generation
```

This means that a successful HTTP/model invocation does not necessarily imply successful structured-output parsing.

The current router intentionally contains the following fail-safe behavior:

```text
missing verification_result
→ stop adaptive research
→ final report
```

This prevents infinite loops, but it may prematurely terminate adaptive research when the verifier itself fails to produce a structured result.

---

### Why Existing Retry May Be Insufficient

The current model uses `.with_retry(...)`.

This generally handles exceptions such as:

```text
API error
timeout
connection failure
parsing exception
```

However, if the structured-output layer returns:

```python
None
```

without raising an exception, the retry mechanism may treat the invocation as successful and therefore not retry it.

Consequently:

```text
HTTP success
!=
VerificationResult success
```

The verifier needs an additional result-validation layer.

---

### Proposed Future Improvement

Add explicit validation after structured-output generation.

Conceptually:

```python
verification_result = await verification_model.ainvoke(...)

if verification_result is None:
    raise VerificationOutputError(
        "Evidence verifier returned an empty structured result."
    )
```

Then integrate this validation into the verifier retry mechanism so that an empty or invalid structured result is treated as a retryable verifier failure.

Desired behavior:

```text
Verifier call
↓
Valid VerificationResult?
├─ Yes → update state normally
└─ No
    ↓
retry verifier
    ↓
retry limit reached?
├─ No → try again
└─ Yes → fall back safely
```

The final fallback can remain:

```text
verification_result unavailable
→ final_report_generation
```

because workflow safety should still take priority over uncontrolled loops.

---

### Possible Additional Improvements

Future versions may also consider:

1. Logging the raw structured-output failure reason.
2. Distinguishing:

   * API invocation failure
   * structured-output parsing failure
   * empty structured result
   * schema validation failure
3. Adding a dedicated verifier retry configuration such as:

```python
max_verification_output_retries
```

instead of sharing generic model retry settings.
4. Using an explicit repair pass when malformed JSON is returned.
5. Adding a regression test where:

* first verifier attempt returns `None`
* second attempt returns a valid `VerificationResult`
* adaptive research continues normally.

6. Improving checkpoint serialization support for custom state models such as `VerificationResult`.

---

### Current Decision

Do **not** implement this robustness extension in the current Adaptive Research V1.

For now:

```text
verification_result is valid
→ normal adaptive routing

verification_result is None
→ existing fail-safe routes to final report
```

The current development priority is to validate the main adaptive research loop:

```text
Research
→ Evidence Verifier
→ Gap Detection
→ Targeted Research
→ Evidence Verifier
→ Final
```

Structured-output robustness will be handled as a separate reliability improvement after the main adaptive research workflow has been validated.


## 当前优先级

当前暂不实现以上两项。

## Dynamic Model Router — Future Improvements

### 1. Model-aware Token Estimation

The current Router uses a lightweight character-based heuristic to estimate prompt token usage. This approach keeps routing inexpensive and provider-independent, but its accuracy can vary significantly across languages, model tokenizers, structured prompts, tool schemas, and mixed Chinese/English inputs.

A future version should introduce model-aware token estimation. Instead of estimating token count once before model selection, the Router can estimate the effective context size independently for every candidate model using that model's tokenizer or tokenizer-compatible estimator.

The compatibility check can then become candidate-specific:

```text
Task Input
   ↓
Candidate Model
   ↓
Model-specific Tokenizer
   ↓
Estimated Input Tokens
   +
Reserved Output Tokens
   +
Runtime / Tool / Schema Overhead
   ↓
Context Capacity Check
```

This would improve routing accuracy near model context-window limits and reduce both false rejections and runtime context-overflow errors.

The current fixed `context_safety_margin_tokens` should also evolve into an adaptive safety-margin strategy based on model context size, tool schema size, structured-output schemas, message count, and tokenizer estimation uncertainty.

---

### 2. More Robust Task Complexity Estimation

The current complexity estimator is intentionally lightweight and deterministic. It uses prompt length, task type, research dimensions, and keyword signals to classify tasks as `SIMPLE`, `MEDIUM`, or `COMPLEX`.

Keyword matching alone, however, cannot reliably represent user intent. In particular, negation and exclusion clauses can invert the meaning of detected keywords.

For example:

```text
无需比较两个框架，也不需要分析性能，只需要查询当前版本。
```

A naive keyword-based estimator may detect `比较`, `性能`, and `当前` and incorrectly increase the complexity score even though the user explicitly excludes comparison and performance analysis.

Future improvements should move from keyword detection toward requirement extraction.

A deterministic requirement parser could identify:

* requested dimensions;
* explicitly excluded dimensions;
* number of independent questions;
* number of entities to investigate;
* comparison requirements;
* evidence and citation requirements;
* verification or conflict-resolution requirements;
* time-sensitive information requirements;
* expected number of searches or research branches.

The Router could therefore reason over structured task signals instead of raw keyword presence:

```text
User Request
   ↓
Requirement Parser
   ↓
Requested Requirements
Excluded Requirements
Entity Count
Research Dimensions
Evidence Requirements
Temporal Requirements
   ↓
Complexity Estimator
```

A later version may additionally train a lightweight non-LLM classifier such as Logistic Regression or LightGBM using historical AskFlow routing traces and manually or automatically evaluated task-complexity labels.

This preserves low routing latency and avoids introducing an additional LLM call solely for model selection while allowing the Router to improve from real workload data and benchmarks.
